# mini-pi-agent v0.6 — MCP Remote Capability Adapter

Status: planned. Do not create the `v0.6` implementation branch until v0.5 is validated and integrated into `main`.

---

# 1. Version theme

v0.6 introduces the first **remote capability integration layer**:

> **MCP is not another Agent Runtime. It is a protocol adapter that lets a remote server contribute capabilities to the same runtime contracts already used by local tools and context sources.**

The version exists to answer a practical question:

```text
The runtime already knows how to:
- call models
- stream responses
- schedule local tools
- manage context
- load Skills
- load Extensions

How can the same Agent use tools exposed by another process,
container, machine, or service without teaching AgentLoop
anything about JSON-RPC, HTTP, stdio, sessions or MCP versions?
```

The answer is an **MCP adapter boundary**.

---

# 2. Why v0.6 follows v0.5

The sequence matters:

```text
v0.1  Agent Loop
v0.2  Streaming + ToolScheduler
v0.3  Context Budget + Compaction
v0.4  Skills
v0.5  Extensions / Hooks
v0.6  MCP Remote Capability Adapter
```

By v0.5, the runtime already has stable seams for:

- registering tools;
- scheduling calls;
- intercepting lifecycle boundaries;
- observing execution;
- adding context material;
- owning registrations by extension/source.

Therefore MCP should adapt into those seams rather than create new execution paths.

Wrong architecture:

```text
AgentLoop
  ├── local tool branch
  ├── MCP tool branch
  ├── HTTP branch
  └── stdio branch
```

Required architecture:

```text
MCP Server
    ↓
McpClient / Transport
    ↓
McpToolSource
    ↓
RemoteToolAdapter
    ↓
ToolRegistry
    ↓
Hooks
    ↓
ToolScheduler
    ↓
normal Agent Loop
```

The Agent Loop must not know whether a Tool is local or remote.

---

# 3. Protocol-version rule

MCP protocol details evolve independently from mini-pi-agent.

The implementation must therefore separate:

```text
Agent-facing contracts
        │
        ▼
MCP capability adapter
        │
        ▼
MCP client facade
        │
        ▼
protocol/version/transport implementation
```

Do not encode handshake assumptions such as:

```text
initialize
notifications/initialized
Mcp-Session-Id
```

into Agent, ToolRegistry, ToolScheduler or RemoteToolAdapter.

The MCP client layer owns version negotiation and protocol-era behavior.

The educational lesson is:

> Protocol compatibility belongs at the protocol boundary, not in the application core.

---

# 4. Primary mental model

A remote tool should look like a local Tool after adaptation.

```text
Remote MCP descriptor

{
  name,
  description,
  inputSchema
}

        ↓ adapt

mini-pi Tool

{
  name,
  description,
  inputSchema,
  execute(args, context)
}
```

The executor is simply remote:

```text
Tool.execute()
      ↓
McpClient.callTool()
      ↓
transport
      ↓
remote MCP server
      ↓
MCP result
      ↓
ToolResult
```

This is the central invariant of v0.6.

---

# 5. Capability model

MCP servers may expose multiple capability families.

v0.6 should recognize three concepts:

```text
Tools      → actions
Resources  → readable context/data
Prompts    → reusable prompt templates
```

However, this version has one primary integration target:

> **Tools are fully integrated into the Agent execution path.**

Resources and prompts should be represented by clean client/source interfaces and demonstrated, but they must not force a second Agent execution engine.

Explicit non-goals:

- MCP server implementation framework;
- generalized remote filesystem abstraction;
- roots/sampling/logging compatibility layer;
- task orchestration platform;
- OAuth implementation from first principles;
- every MCP extension proposal;
- hiding network failures from the model.

```text
                 │                │
```

```text

     ↓

     ↓
```

No bypass path is allowed.

# 7. McpClientFacade

Do not expose a concrete SDK client throughout the codebase.

Introduce a small internal facade:

```ts
export interface McpClientFacade {
  readonly id: string;

  connect(signal: AbortSignal): Promise<void>;
  close(): Promise<void>;

  listTools(signal: AbortSignal): Promise<McpToolDescriptor[]>;

  callTool(
    name: string,
    args: Record<string, JsonValue>,
    signal: AbortSignal
  ): Promise<McpToolCallResult>;

  listResources?(signal: AbortSignal): Promise<McpResourceDescriptor[]>;
  readResource?(
    uri: string,
    signal: AbortSignal
  ): Promise<McpResourceContent[]>;

  listPrompts?(signal: AbortSignal): Promise<McpPromptDescriptor[]>;
  getPrompt?(
    name: string,
    args: Record<string, string>,
    signal: AbortSignal
  ): Promise<McpPromptResult>;
}
```

Why a facade?

```text
mini-pi-agent contracts
        ≠
MCP SDK release API
        ≠
wire protocol
```

The facade protects the runtime from SDK churn.

# 8. Connection configuration

Represent connection intent independently from transport implementation.

```ts
export type McpServerConfig =
  | {
      id: string;
      transport: "stdio";
      command: string;
      args?: string[];
      env?: Record<string, string>;
    }
  | {
      id: string;
      transport: "http";
      url: string;
      headers?: Record<string, string>;
    };
```

Important rules:

1. server IDs are stable local identities;
2. tool names are not assumed globally unique;
3. secrets must not be written into traces by default;
4. transport config is not copied into Tool metadata sent to the model;
5. connection lifecycle belongs to the MCP layer.

---

# 9. McpConnectionManager

A single server is simple; multiple servers require lifecycle ownership.

Introduce:

```ts
export interface McpConnectionManager {
  connect(config: McpServerConfig, signal: AbortSignal): Promise<McpConnection>;
  disconnect(serverId: string): Promise<void>;
  get(serverId: string): McpConnection | undefined;
  list(): readonly McpConnection[];
  closeAll(): Promise<void>;
}
```

State model:

```text
disconnected
    ↓
connecting
    ↓
connected
    ↓
closing
    ↓
disconnected

failure can transition to:
error
```

Do not hide connection state inside individual tools.

# 10. Remote tool descriptor

Keep remote metadata distinct from local runtime Tool objects.

```ts
export interface McpToolDescriptor {
  name: string;
  description?: string;
  inputSchema: JsonSchema;
  outputSchema?: JsonValue;
}
```

The adapter adds ownership/provenance:

```ts
export interface RemoteToolIdentity {
  serverId: string;
  remoteName: string;
  localName: string;
}
```

This distinction becomes essential once two servers expose the same name.

---

# 11. Tool naming and collisions

Suppose:

```text
server github → tool search
server docs   → tool search
```

Do not silently overwrite one.

Recommended local naming policy:

```text
<server-id>__<tool-name>
```

Example:

```text
github__search
docs__search
```

A future alias layer may expose friendlier names when unique.

v0.6 invariant:

> Remote identity and local registry identity must be explicit and deterministic.

Collision behavior must be tested.

# 12. RemoteToolAdapter

Core adapter:

```ts
export class RemoteToolAdapter implements Tool {
  constructor(
    readonly identity: RemoteToolIdentity,
    readonly descriptor: McpToolDescriptor,
    private readonly client: McpClientFacade
  ) {}

  get name() {
    return this.identity.localName;
  }

  get description() {
    return this.descriptor.description ?? "";
  }

  get inputSchema() {
    return this.descriptor.inputSchema;
  }

  async execute(args, context) {
    const result = await this.client.callTool(
      this.identity.remoteName,
      args,
      context.signal
    );

    return normalizeMcpToolResult(result);
  }
}
```

Important:

```text
RemoteToolAdapter
should be boring.
```

It translates contracts. It does not own:

- retries;
- global timeout policy;
- permissions;
- scheduling;
- context compaction;
- UI rendering.

Those belong to existing runtime layers.

# 13. McpToolSource

Discovery and registration are separate from invocation.

```ts
export interface McpToolSource {
  discover(
    connection: McpConnection,
    signal: AbortSignal
  ): Promise<RemoteToolAdapter[]>;
}
```

Lifecycle:

```text
connect server
     ↓
list tools
     ↓
adapt descriptors
     ↓
register under owner = mcp:<server-id>
     ↓
Agent may call normally
```

On disconnect:

```text
owner = mcp:<server-id>
     ↓
unregister all owned tools
```

This directly reuses v0.5 registration ownership.

# 14. Dynamic tool-list changes

A server's capability catalog may change while connected.

Design a generic invalidation mechanism:

```text
server announces tool catalog change
         ↓
MCP client callback / subscription
         ↓
McpToolSource.refresh(serverId)
         ↓
diff descriptors
         ↓
atomic registry update
```

Do not couple AgentLoop to MCP notifications.

Registry refresh must satisfy:

```text
old catalog OR new catalog
```

not an externally visible half-updated mixture.

If the selected SDK/protocol era supports list-change subscription differently, that complexity remains inside the MCP facade.

---

# 15. Tool result normalization

MCP results may contain richer content than the current simple string ToolResult.

v0.6 must not solve this by leaking raw protocol objects into AgentMessage.

Introduce a normalization boundary.

Educational first step:

```ts
export interface NormalizedToolContent {
  text: string;
  isError: boolean;
  metadata?: Record<string, JsonValue>;
}
```

Normalization policy:

```text
MCP content blocks
      ↓
normalize
      ↓
mini-pi ToolResult
```

Text remains the universal fallback representation.

If structured output is preserved, keep it in optional metadata rather than making the core loop depend on MCP-specific schemas.

---

# 16. Error model

Network/protocol errors are different from valid remote tool failures.

Keep these concepts distinguishable:

```text
TransportFailure
ProtocolFailure
RemoteToolFailure
Cancellation
Timeout
```

At the Agent observation boundary, recoverable failures normally become ToolResult errors so the model can reason about them.

Example:

```text
remote server unavailable
        ↓
RemoteToolAdapter / facade error
        ↓
ToolScheduler catches execution failure
        ↓
ToolResultMessage(isError=true)
        ↓
model can retry, choose another tool, or explain failure
```

Fatal corruption of runtime invariants may still abort the run.

---

# 17. Cancellation and timeout

Do not invent MCP-specific cancellation policy in ToolScheduler.

Existing propagation remains:

```text
Agent.abort()
    ↓
root AbortSignal
    ↓
ToolScheduler
    ↓
RemoteToolAdapter
    ↓
McpClientFacade.callTool(... signal)
    ↓
transport / SDK
```

Per-tool timeout also remains scheduler policy.

The MCP layer's job is only to honor the provided signal as faithfully as the underlying transport allows.

---

# 18. Retries

Do not automatically retry arbitrary remote tool calls.

Why?

```text
read-like tool       → maybe idempotent
create_issue         → side effect
send_message         → side effect
charge_card          → side effect
```

The runtime usually cannot infer whether repeating a tool call is safe.

v0.6 policy:

```text
connection/discovery retry may exist with care
business tool-call retry is NOT automatic by default
```

Future annotations/policies may improve this.

---

# 19. Hooks integration

MCP tools must pass through the exact same hooks as local tools.

```text
Remote ToolCall
      ↓
before_tool
      ↓
ToolScheduler
      ↓
RemoteToolAdapter
      ↓
after_tool
```

This allows v0.5 extensions to:

- inspect remote calls;
- block calls;
- rewrite arguments;
- audit results;
- attach metadata.

Do not introduce:

```text
before_mcp_tool
```

unless a future requirement cannot be expressed through generic Tool hooks.

Prefer generic runtime contracts.

---

# 20. Future permission integration

v0.8 will introduce permission/sandbox policy.

v0.6 must prepare for it by preserving provenance:

```ts
interface ToolProvenance {
  kind: "local" | "extension" | "mcp";
  sourceId?: string;
}
```

Then future policy can ask:

```text
Is this a remote MCP tool?
Which server owns it?
What is its name?
```

without parsing naming conventions.

Do not implement full permission policy in v0.6.

---

# 21. Resources

MCP Resources are conceptually context/data sources, not Tools.

Model them separately:

```ts
export interface McpResourceDescriptor {
  uri: string;
  name?: string;
  description?: string;
  mimeType?: string;
}
```

Flow:

```text
MCP resource
    ↓
McpClientFacade.readResource()
    ↓
ContextSupplement / explicit user-visible content
    ↓
ContextPlanner
```

Do not register every resource as a Tool automatically.

This preserves:

```text
Capability/action ≠ Context/data
```

v0.6 only needs a small demonstration proving the distinction.

---

# 22. Prompts

MCP Prompts are reusable prompt templates.

Treat them as another source of model guidance:

```text
MCP prompt template
      ↓
getPrompt(name,args)
      ↓
rendered prompt messages/content
      ↓
ContextPlanner or explicit user action
```

Do not make prompts executable tools unless explicitly adapted for a UX reason.

This preserves:

```text
Tool     = action
Resource = data/context
Prompt   = reusable guidance/template
```

---

# 23. Transport model

v0.6 should teach at least two deployment shapes:

```text
stdio
────────────────
Agent process
   ↓ child process pipes
MCP server process


HTTP
────────────────
Agent process
   ↓ network request/stream
MCP server
```

But Transport is below `McpClientFacade`.

The Agent runtime should not contain:

```ts
if (transport === "stdio") { ... }
if (transport === "http") { ... }
```

outside the MCP connection layer.

# 24. Testing without external infrastructure

Do not make the unit test suite depend on public MCP servers.

Introduce a fake/in-memory facade:

```ts
class FakeMcpClient implements McpClientFacade {
  // deterministic tool catalog and scripted results
}
```

Use it to prove:

- tool discovery;
- adaptation;
- naming;
- registration ownership;
- invocation;
- result normalization;
- cancellation;
- failures;
- catalog refresh.

Then add a small integration fixture server for transport tests.

Tests should remain deterministic and offline.

Add MCP lifecycle events at the integration layer, not inside AgentLoop:

```text
mcp_connect_start
mcp_connected
mcp_connect_error
mcp_disconnected
mcp_catalog_refresh
```

Tool execution itself continues to use generic:

```text
tool_start
tool_end
```

This distinction is important:

```text
connection lifecycle → MCP-specific events
execution lifecycle  → generic Tool events
```

# 29. Security boundary

An MCP server is an external capability provider.

Treat all remote metadata and output as untrusted input.

v0.6 baseline rules:

- validate tool descriptors before registration;
- validate tool-call arguments through existing ToolRegistry rules;
- cap/normalize unusually large result content through existing context policies;
- never log configured secrets/authorization headers by default;
- preserve server provenance;
- do not execute server-supplied local code;
- do not treat descriptions as trusted system instructions.

Full user approval and sandbox policy remain v0.8.

---

# 30. Explicit non-goals

v0.6 intentionally does not implement:

- an MCP server framework;
- all current/future MCP features;
- custom auth flows from first principles;
- autonomous server installation;
- hidden retries for side-effecting calls;
- MCP-specific scheduling semantics;
- MCP-specific permission semantics;
- distributed service discovery;
- production connection pooling;
- multi-tenant credentials;
- generalized gateway/load balancer.

Keep the version centered on one idea:

> **Adapt remote capabilities into stable local runtime contracts.**

# 33. Learning goals

After v0.6, a reader should be able to explain:

1. why MCP is not an Agent Loop;
2. why a remote MCP tool can be adapted to the same Tool interface as a local function;
3. why protocol-version negotiation belongs below runtime contracts;
4. why transport and capability discovery are separate concerns;
5. why ToolScheduler should not care whether execution is local or remote;
6. why remote tool provenance matters;
7. why two servers may require deterministic tool namespacing;
8. why Tool, Resource and Prompt represent different semantic categories;
9. why remote errors should usually become observations rather than crash the runtime;
10. why automatic retries are dangerous for side-effecting remote tools;
11. why registration ownership from v0.5 makes MCP disconnect/reload tractable;
12. how later permission policy can govern remote tools without MCP-specific branches.

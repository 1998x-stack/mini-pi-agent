# mini-pi-agent v0.3 — Context Budget & Compaction

Status: planned. Do not create the `v0.3` implementation branch until v0.2 is validated and integrated into `main`.

---

# 1. Version theme

v0.3 introduces the first long-running-agent memory pressure model:

> **Durable history remains complete; model-visible context is a derived, budgeted projection of that history.**

The version exists to answer a practical question:

```text
If an agent can run for hundreds of turns,
why does its prompt not grow forever?
```

The answer must not be:

```text
delete old messages
```

Instead, v0.3 makes three different objects explicit:

```text
Runtime State
     │
     ├──────────────► Durable Session History
     │                    append-only truth
     │
     └──────────────► Model Context
                          temporary projection
                          constrained by budget
```

---

# 2. Why v0.3 follows v0.2

v0.1 teaches the feedback loop:

```text
model → tool → observation → model
```

v0.2 teaches asynchronous transport and tool scheduling:

```text
stream → assemble → schedule → ordered observations
```

Only after those semantics are stable should the runtime decide **which historical information enters each model call**.

If compaction is added earlier, bugs in model/tool ordering and bugs in context selection become difficult to distinguish.

v0.3 therefore treats context preparation as a separate subsystem around a stable Agent Loop.

---

# 3. Primary mental model

The core transformation is:

```text
Complete Session History
          │
          ▼
      ContextPlanner
          │
          ├── preserve system instructions
          ├── preserve recent messages
          ├── preserve unresolved tool-call/result pairs
          ├── reuse summaries/checkpoints
          ├── truncate oversized observations
          └── estimate token cost
          │
          ▼
     ContextBudget
          │
          ▼
 Model-visible AgentMessage[]
```

The most important invariant is:

> **Compaction changes what the model sees; it must not rewrite or destroy the durable session history.**

---

# 4. Core distinction: history is not context

## Durable session history

The session store remains the audit log of what actually happened:

```text
user
assistant
ToolCall
ToolResult
assistant
...
```

Properties:

- append-only by default;
- complete enough for replay/audit;
- independent of provider context limits;
- future session branching can refer to exact historical entries.

## Model context

The model context is rebuilt for each turn:

```text
system prompt
summary/checkpoint
selected historical messages
recent messages
current user/steering input
```

Properties:

- ephemeral;
- provider/model dependent;
- budget constrained;
- may omit raw historical detail;
- may contain synthesized summary entries.

## Runtime state

Runtime state tracks execution concerns such as:

- current run id;
- turn number;
- message list reference;
- running/cancelled state;
- queues;
- tracing metadata.

It is neither the durable storage format nor the exact provider prompt.

# 5. Proposed architecture

```text
                    Agent Loop
                        │
                        │ before provider call
                        ▼
                ContextPipeline
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
 TokenEstimator    ContextBudget     CompactionPolicy
        │               │                │
        └───────────────┼────────────────┘
                        ▼
                 ContextPlanner
                        │
            ┌───────────┴───────────┐
            ▼                       ▼
       raw messages          SummaryStore / entries
            │                       │
            └───────────┬───────────┘
                        ▼
              PreparedContext
                        │
                        ▼
                  LLMProvider
```

`runAgentLoop()` should know only that it asks a context component to prepare messages. It should not contain token-counting or summarization branches.

# 6. New contracts

## 6.1 TokenEstimator

```ts
export interface TokenEstimator {
  estimateMessages(messages: readonly AgentMessage[]): number;
  estimateText(text: string): number;
}
```

The first implementation may be approximate and deterministic.

The architecture matters more than perfect tokenizer parity in v0.3.

Possible reference implementation:

```text
ApproxTokenEstimator
≈ characters / 4
+ small per-message overhead
```

Provider-specific exact tokenizers can be added later without changing the planner.

---

## 6.2 ContextBudget

```ts
export interface ContextBudget {
  maxInputTokens: number;
  reservedOutputTokens: number;
  softLimitRatio: number;
}
```

Example:

```text
model context window      32,000
reserved output            4,000
hard input budget          28,000
soft threshold (80%)       22,400
```

The soft threshold allows compaction before a provider hard failure.

---

## 6.3 PreparedContext

```ts
export interface PreparedContext {
  messages: AgentMessage[];
  estimatedTokens: number;
  compacted: boolean;
  droppedMessageCount: number;
  summaryIds: string[];
}
```

This object makes context decisions observable and testable.

---

## 6.4 ContextPlanner

```ts
export interface ContextPlanner {
  prepare(input: {
    systemPrompt: string;
    history: readonly AgentMessage[];
    budget: ContextBudget;
    signal: AbortSignal;
  }): Promise<PreparedContext>;
}
```

The planner owns selection policy.

The provider must not decide which messages to discard.

# 7. Compaction is not one algorithm

v0.3 should implement compaction as composable stages.

Recommended reference pipeline:

```text
raw history
   ↓
normalize tool-call/result boundaries
   ↓
truncate individually huge tool results
   ↓
keep recent window
   ↓
identify older compactable region
   ↓
summary/checkpoint old region
   ↓
re-estimate
   ↓
repeat/fallback if still over budget
```

This keeps the policy inspectable.

---

# 8. Tool-result truncation

Tool output can dominate context faster than conversation text.

Example:

```text
shell("cat giant.log")
        ↓
2 MB output
```

The session should preserve the original result if that is the durable-history policy, but model context may use a reduced representation.

Proposed policy:

```ts
export interface ToolResultReducer {
  reduce(
    message: ToolResultMessage,
    targetTokens: number
  ): ToolResultMessage;
}
```

Reference strategy:

```text
head
...
<truncated N chars/tokens>
...
tail
```

Why keep both head and tail?

- command output often puts headers/configuration first;
- failures and summaries often appear near the end.

The reduced message must clearly state that truncation occurred.

---

# 9. Summary checkpoint model

A summary should be an explicit runtime artifact, not invisible mutation.

Proposed internal type:

```ts
export interface ContextSummary {
  id: string;
  fromMessageIndex: number;
  toMessageIndex: number;
  content: string;
  estimatedTokens: number;
  createdAt: number;
}
```

Conceptually:

```text
messages 0..120
      │
      ▼
 summary S1
      │
      ├── decisions
      ├── files changed
      ├── unresolved tasks
      ├── important tool observations
      └── constraints

messages 121..145 remain raw
```

The summary references the historical interval it represents.

Later v0.7 session branching can therefore reason about which branch/history range a summary belongs to.

---

# 10. Summary content requirements

A useful coding-agent summary should preserve categories rather than merely paraphrase conversation prose.

Recommended structure:

```text
Goal
Decisions
Constraints
Files/Artifacts
Tool findings
Current state
Open work
Errors/risks
```

For example:

```text
Goal:
- add streaming tool-call support

Decisions:
- Tool remains scheduling-agnostic
- scheduler owns concurrency policy

Files changed:
- src/llm/streaming/assembler.ts
- src/scheduler/sequential.ts

Tests:
- fragmented tool arguments covered

Open work:
- cancellation integration test
```

This is more durable than a narrative summary such as "the user and assistant discussed streaming".

# 11. Initial compaction strategy

The first reference strategy should be intentionally simple.

## Before soft limit

```text
history estimate <= soft limit
→ return full context
```

## Between soft and hard limit

```text
keep:
- system prompt
- latest existing summary
- recent raw messages

compact:
- oldest eligible raw region
```

## Above hard limit after summary

Apply fallback stages in deterministic order:

```text
1. reduce oversized tool results
2. shrink recent-history target
3. compact an additional older region
4. fail with ContextBudgetExceededError if invariant-preserving reduction is impossible
```

Never silently send an oversized request and hope the provider accepts it.

---

# 12. Message-boundary invariants

Compaction must not split semantic pairs carelessly.

Important examples:

```text
AssistantMessage(toolCalls=[A,B])
ToolResult(A)
ToolResult(B)
```

should be treated as one logical interaction unit when selecting/compacting history.

Do not retain:

```text
ToolResult(B)
```

while dropping the assistant message that introduced call B unless the summary explicitly carries the necessary context.

Likewise, avoid context containing an unresolved tool call with no result unless it is genuinely the current in-flight state.

---

# 13. Recency window

The planner should preserve a recent raw window because summaries are lossy.

Possible initial configuration:

```ts
export interface KeepRecentPolicy {
  minMessages: number;
  targetTokens: number;
}
```

Example:

```text
summary of turns 1..40
+ raw turns 41..50
```

rather than:

```text
one summary of everything
```

This keeps local reasoning detail available to the model.

---

# 14. Summarizer abstraction

Do not hard-code summary generation into the planner.

```ts
export interface ContextSummarizer {
  summarize(input: {
    messages: readonly AgentMessage[];
    previousSummary?: ContextSummary;
    signal: AbortSignal;
  }): Promise<ContextSummary>;
}
```

Two implementations are useful for education/tests:

```text
DeterministicSummarizer
- no network
- extracts roles/tool names/key text
- stable tests

LLMSummarizer
- asks configured model to produce structured compact summary
```

Unit tests must use the deterministic implementation.

---

# 15. Incremental summary reuse

Do not resummarize the full past on every turn.

Preferred progression:

```text
S1 = summarize(messages 0..100)

later:
S2 = summarize(
  previousSummary = S1,
  messages = 101..160
)
```

This teaches a core long-running-agent idea:

```text
historical raw log
       ↓
progressive checkpoints
       ↓
small working context
```

But the original historical log remains available in storage.

---

# 16. Context events

Add observability events such as:

```ts
{ type: "context_prepare_start", ... }
{ type: "context_estimated", tokens: number, ... }
{ type: "context_compaction_start", ... }
{ type: "context_summary_created", ... }
{ type: "tool_result_reduced", ... }
{ type: "context_prepare_end", beforeTokens, afterTokens, ... }
```

These events allow CLI/trace tooling to answer:

```text
Why did the model suddenly lose raw history?
How much did compaction save?
Which interval was summarized?
Was a tool result truncated?
```

No UI-specific formatting belongs in the planner.

---

# 17. Failure semantics

Compaction may itself fail.

Examples:

- summarizer provider failure;
- cancellation;
- malformed summary artifact;
- budget still impossible after compaction;
- one indivisible recent message exceeds the entire budget.

Define explicit errors:

```ts
ContextBudgetExceededError
ContextCompactionError
```

Policy suggestion:

- deterministic local reductions may continue after summarizer failure if safe;
- never destroy durable history;
- never silently omit the current user request;
- never silently remove unmatched current tool state.

# 20. Test matrix

## Budget tests

- below soft limit: no compaction;
- above soft limit: planner compacts;
- output reserve is respected;
- impossible budget fails explicitly.

## Interaction-boundary tests

- assistant tool call + results stay logically grouped;
- recent user message is never dropped;
- in-flight interaction remains valid.

## Tool-result tests

- small result unchanged;
- large result reduced;
- head and tail retained;
- marker reports truncation;
- durable session still stores original result.

## Summary tests

- summary covers exact index range;
- repeated preparation reuses summary;
- incremental summary extends prior checkpoint;
- deterministic summarizer produces stable tests.

## Cancellation tests

- cancellation stops LLM summary generation;
- cancellation does not corrupt existing summary state;
- next run can continue from durable history.

## Integration tests

Construct a synthetic long conversation and prove:

```text
history grows monotonically
model-visible context remains under budget
recent messages remain raw
old region becomes summary
provider receives valid tool-call/result structure
```

# 23. Architectural invariants

The following statements must remain true after v0.3:

```text
SessionStore owns durable history.
ContextPlanner owns model-visible selection.
TokenEstimator owns cost estimation.
Summarizer owns compression content generation.
ToolResultReducer owns large-observation reduction.
LLMProvider receives prepared context but does not own compaction policy.
Agent Loop orchestrates these contracts but does not implement their internals.
```

The architectural health check is:

> Could we replace the compaction policy without changing `Tool`, `ToolScheduler`, `SessionStore`, or provider implementations?

If not, the boundaries are wrong.

---

# 24. What v0.3 should teach

After completing this version, a reader should be able to explain:

1. why session history and model context are different;
2. why compaction must not destructively truncate history;
3. why token budget is a runtime resource-management problem;
4. why tool output often dominates context usage;
5. why message/tool-result boundaries matter during trimming;
6. why recent raw context should coexist with older summaries;
7. why summaries should reference the historical range they represent;
8. why progressive checkpointing is cheaper than repeatedly summarizing all history;
9. why the provider should not own context policy;
10. how this architecture prepares the project for v0.7 session branching without corrupting history.

---

# 25. Next version dependency

Once v0.3 makes model context bounded and stable, v0.4 can safely introduce **Skills**.

The sequence matters:

```text
v0.1 execution loop
   ↓
v0.2 streaming + scheduling
   ↓
v0.3 bounded working context
   ↓
v0.4 skills / workflow knowledge
```

Skills can add instructions/resources to context, so the runtime should understand context ownership and budget **before** a skill system begins injecting more material.

# v0.3 — Context Budget & Compaction

Status: **active design snapshot on branch `v0.3`**.

This document is the detailed version design. Root `version.md` is the branch identity and acceptance contract; `Plan.md` remains the repository-wide roadmap.

---

# 1. Problem statement

A useful agent accumulates history quickly:

```text
user request
assistant reasoning/output
tool call
tool result
assistant follow-up
more tool calls
large logs
source files
errors
retries
```

If every historical byte is resent to the model forever, the runtime eventually hits one or more limits:

- provider context-window limit;
- latency growth;
- input-token cost growth;
- attention dilution;
- huge environment observations dominating useful context.

The naive fixes are architecturally wrong:

```text
wrong #1: delete old session messages
wrong #2: keep only the last N messages
wrong #3: silently truncate large tool output
wrong #4: summarize everything every turn
wrong #5: add a vector database before defining context lifecycle
```

v0.3 creates a first-principles context lifecycle instead.

---

# 2. Fundamental separation

The central invariant is:

```text
DURABLE HISTORY
full historical truth
append-only semantics
replay/debug value
        │
        │ derive
        ▼
MODEL CONTEXT
bounded projection
summaries + recent units
reduced observations
provider-facing payload
```

Runtime state is a third object:

```text
Runtime State
= ephemeral execution state

Durable History
= persistent conversational truth

Prepared Context
= temporary model input
```

They must not collapse into the same array merely because v0.1 started with `messages[]`.

---

# 3. Why message-count trimming is insufficient

The existing `TailContextTransform(maxMessages)` is intentionally simple. It exposes the seam but does not preserve semantic structure.

Example:

```text
AssistantMessage
  toolCalls: [read#1, read#2]

ToolResult read#1
ToolResult read#2
```

A raw tail slice can accidentally produce:

```text
ToolResult read#2
```

without the assistant call that caused it, or preserve the assistant tool call while dropping a required result.

Therefore v0.3 plans context in logical **units**, not arbitrary messages.

---

# 4. ContextUnit model

Target conceptual model:

```ts
export type ContextUnit =
  | UserUnit
  | AssistantTextUnit
  | ToolExchangeUnit
  | SummaryUnit;
```

A `ToolExchangeUnit` groups:

```text
assistant tool-call message
        +
all matching result messages that belong to the exchange
```

The builder validates ordering/identity before compaction policy sees the units.

Important principle:

> Selection policy operates on semantically valid units; it should not need to rediscover message protocol rules.

---

# 5. Budget model

The first budget model is intentionally explicit:

```text
contextWindow
- outputReserve
- safetyMargin
=
maximum estimated model input
```

Example:

```text
context window  = 128000
output reserve  =  12000
safety margin   =   4000
--------------------------------
input budget    = 112000
```

The budget object is policy data, not provider transport state.

Recommended type:

```ts
export interface ContextBudget {
  contextWindow: number;
  outputReserve: number;
  safetyMargin: number;
}
```

Derived values should be calculated in one place and reject impossible configurations.

---

# 6. Token estimation

v0.3 should not begin by importing model-specific tokenizer complexity.

Reference interface:

```ts
export interface TokenEstimator {
  estimateText(text: string): number;
  estimateMessage(message: AgentMessage): number;
  estimateMessages(messages: readonly AgentMessage[]): number;
}
```

Reference implementation may use deterministic approximation, for example UTF-8/character-based heuristics plus fixed message overhead.

Why approximate first?

```text
architecture testability
      >
perfect provider accounting
```

Later adapters can provide more accurate estimators without changing the planner.

---

# 7. PreparedContext

The planner should return more than just messages.

Recommended shape:

```ts
export interface PreparedContext {
  systemPrompt: string;
  messages: AgentMessage[];
  estimatedInputTokens: number;
  budget: ContextBudget;
  compacted: boolean;
  provenance: ContextProvenance;
}
```

Provenance should explain decisions such as:

```text
history units: 83
selected recent units: 17
summary reused: summary_002
large tool results reduced: 3
estimated before: 184230
estimated after: 48310
```

This makes compaction inspectable instead of magical.

---

# 8. ContextPlanner contract

The planner is the main v0.3 boundary:

```ts
export interface ContextPlanner {
  prepare(input: ContextPlanInput): Promise<PreparedContext>;
}
```

Input should include:

- system prompt;
- complete current history;
- budget;
- cancellation signal;
- optional summaries/checkpoints.

It should not include:

- JSONL file handles;
- provider HTTP transport;
- CLI rendering;
- Skill-specific knowledge;
- MCP-specific resources.

Those belong elsewhere.

---

# 9. Selection strategy: newest useful context first

The first deterministic planner should be understandable without an LLM:

```text
1. reserve mandatory system material
2. preserve newest valid context units
3. reduce oversized tool observations where needed
4. stop when budget is reached
5. return explicit provenance
```

This becomes the readable baseline analogous to the sequential scheduler in v0.2.

Only after this baseline is correct should summarization be introduced.

---

# 10. Large tool observations

Tool output often dominates context:

```text
compiler log
large JSON
source file
search result dump
stack trace
repository listing
```

Introduce a dedicated `ToolResultReducer`:

```ts
export interface ToolResultReducer {
  reduce(
    message: ToolResultMessage,
    targetTokens: number
  ): Promise<ToolResultMessage>;
}
```

Reference policy:

```text
small result
  -> unchanged

large result
  -> explicit metadata/header
  -> keep head
  -> omission marker
  -> keep tail
```

The original durable message remains untouched.

---

# 11. Why head + tail

Many environment outputs put useful information at both ends:

```text
HEAD
configuration
command
file identity
headers

MIDDLE
bulk repetitive output

TAIL
error
summary
exit status
final diagnostic
```

Therefore a deterministic head/tail reducer is a useful educational baseline.

It is not claimed to be universally optimal.

---

# 12. Summary artifact

A summary is a derived artifact with identity and provenance.

Conceptual type:

```ts
export interface ContextSummary {
  id: string;
  content: string;
  coveredThrough: number;
  estimatedTokens: number;
  createdAt: number;
}
```

The real implementation may use a stronger historical cursor than a raw array index, especially once v0.7 adds branching.

For v0.3, the critical property is explicit coverage/provenance.

---

# 13. Structured summary format

Prefer summaries that preserve state rather than prose-only compression:

```text
# Goal
...

# Decisions
...

# Constraints
...

# Important findings
...

# Files/artifacts changed
...

# Current state
...

# Open work
...
```

A coding agent needs task state, not a literary recap.

---

# 14. Deterministic summarizer first

Tests must not require a live LLM.

Therefore define:

```ts
export interface ContextSummarizer {
  summarize(input: SummaryInput): Promise<ContextSummary>;
}
```

Provide a deterministic/fake summarizer for tests.

A provider-backed summarizer can be an optional adapter/example after planner semantics are proven.

---

# 15. SummaryStore

Summary storage is separate from session history.

Target seam:

```ts
export interface SummaryStore {
  latest(): Promise<ContextSummary | undefined>;
  save(summary: ContextSummary): Promise<void>;
}
```

Why separate?

- durable conversation messages are historical truth;
- summaries are derived acceleration/checkpoint artifacts;
- summaries may be regenerated;
- future branch-aware summaries may differ by branch head.

---

# 16. Progressive compaction algorithm

Reference policy:

```text
if full context fits
    use full context
else
    reduce large tool observations

if reduced context fits
    use it
else
    keep a recent window
    summarize the older eligible prefix
    combine summary + recent window
```

On later compaction:

```text
previous summary
+
newly old units
        ↓
next summary
```

This avoids repeatedly summarizing the entire raw lifetime.

---

# 17. Unsatisfied budget behavior

Some inputs cannot fit even after normal compaction:

```text
system prompt alone too large
single mandatory recent unit too large
summary + minimum recent context still too large
```

Do not silently send an oversized request.

Define an explicit error such as:

```ts
class ContextBudgetExceededError extends Error {
  requiredTokens: number;
  availableTokens: number;
}
```

Failure should be deterministic and observable.

---

# 18. Cancellation

A summarizer may invoke an LLM or perform I/O.

Cancellation path:

```text
Agent.abort()
    ↓
AbortSignal
    ↓
ContextPlanner
    ↓
ContextSummarizer
```

Compaction work must not become an uncancellable hidden pre-model phase.

---

# 19. Events / observability

Recommended additions:

```text
context_prepare_start
context_reduced
context_summary_start
context_summary_end
context_prepare_end
context_budget_error
```

Events should expose estimates and counts, not dump secret/full model context by default.

---

# 20. Integration point

Today the loop has a `ContextTransform` seam.

Migration target:

```text
history
   ↓
ContextPlanner.prepare(...)
   ↓
PreparedContext
   ↓
LLMRequest
```

Do not place budgeting logic directly in `Agent` or `runAgentLoop()`.

The loop should orchestrate one context-preparation call and consume its result.

# 22. Version milestones

## v0.3.1 — Budget & estimator

Learn: context is a finite resource with explicit accounting.

## v0.3.2 — Context units

Learn: semantic message groups matter more than raw array positions.

## v0.3.3 — Tool-result reduction

Learn: durable observation and model-visible observation can differ.

## v0.3.4 — Deterministic planner

Learn: selection policy is separate from history storage.

## v0.3.5 — Summary artifacts

Learn: summary is derived state with provenance.

## v0.3.6 — Progressive compaction

Learn: long-running state can be checkpointed incrementally.

## v0.3.7 — Runtime integration

Learn: the Agent Loop remains small while context policy grows outside it.

---

# 23. Required acceptance properties

The implementation is not complete unless tests prove:

```text
planning never mutates durable input history

visible tool calls keep their required results

large tool results are reduced explicitly

context estimates remain deterministic

planner stays within budget or raises a typed error

summary coverage is explicit

summary reuse is possible

abort interrupts summarization

Agent sends prepared context while session persists full history
```

---

# 24. Non-goals

Keep out of v0.3:

- embeddings/vector DB;
- relevance ranking across millions of memories;
- autonomous long-term-memory extraction;
- knowledge graphs;
- Skills;
- Extensions;
- MCP;
- branch-aware session DAG semantics;
- sandboxing;
- RPC.

Those are different mental models.

---

# 25. Relationship to v0.4

v0.4 introduces Skill catalogs and loaded instructions.

That only works cleanly if v0.3 already provides:

```text
context supplements
+
budget accounting
+
prepared context
```

Thus v0.3 is the substrate for progressive Skill disclosure.

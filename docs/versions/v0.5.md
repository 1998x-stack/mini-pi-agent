# mini-pi-agent v0.5 — Extensions & Lifecycle Hooks

Status: planned. Do not create the `v0.5` implementation branch until v0.4 is validated and integrated into `main`.

---

# 1. Version theme

v0.5 introduces the first **imperative runtime customization layer**:

> **An Extension is trusted executable code that can register capabilities and intercept explicit runtime lifecycle boundaries without requiring edits to the Agent core.**

The version exists to answer a practical question:

```text
The runtime already knows how to:
- run the model/tool feedback loop
- stream and schedule tools
- budget model context
- load Skills as workflow knowledge

How can a project add behavior such as:
- custom tools
- repository-specific commands
- context injection
- tool-call validation or blocking
- argument rewriting
- post-processing tool results
- run/session metadata

without adding one more `if (...)` branch to Agent or AgentLoop?
```

The answer is **Extensions + explicit lifecycle hooks**.

---

# 2. Why v0.5 follows v0.4

The sequence matters:

```text
v0.1
core feedback loop

v0.2
streaming + scheduling

v0.3
context budgeting

v0.4
Skills = declarative workflow knowledge

v0.5
Extensions = imperative runtime customization
```

A Skill answers:

```text
"How should the model perform this kind of task?"
```

An Extension answers:

```text
"How should the runtime behave at this lifecycle boundary?"
```

That distinction must remain explicit.

```text
Skill
────────────────────
metadata
instructions
references
scripts/assets

changes model guidance


Extension
────────────────────
trusted code
registered tools
commands
hook handlers
runtime-local state

changes runtime behavior
```

A Skill should never need direct access to Agent internals.
An Extension may customize runtime behavior, but only through stable public contracts.

---

# 3. Primary mental model

The Agent Loop should remain conceptually small:

```text
User
 ↓
prepare context
 ↓
Model
 ↓
AssistantMessage
 ↓
Tool calls
 ↓
ToolScheduler
 ↓
Tool results
 ↓
repeat
```

Extensions live around explicit seams:

```text
                    Extension Host
                          │
       ┌──────────────────┼───────────────────┐
       │                  │                   │
       ▼                  ▼                   ▼
 registerTool()      registerCommand()      on(hook)
                                                │
                                                ▼
Run ──► before_run ──► before_model ──► Model ──► after_model
                                      │
                                      ▼
                               before_tool
                                      │
                                      ▼
                                     Tool
                                      │
                                      ▼
                                after_tool
                                      │
                                      ▼
                                  after_turn
                                      │
                                      ▼
                                   after_run
```

The important rule is:

> **The core owns lifecycle semantics. Extensions may participate only through named boundaries.**

---

# 4. Event vs Hook — do not conflate them

v0.1 already has `EventBus`.

That mechanism should remain primarily observational:

```text
Event
────────────────────
agent_start
turn_start
text_delta
tool_start
tool_end
...

Purpose
────────────────────
logging
tracing
metrics
UI rendering
```

An observer should not silently mutate runtime behavior.

v0.5 introduces a separate concept:

```text
Hook
────────────────────
before_run
before_model
before_tool
after_tool
...

Purpose
────────────────────
intercept
validate
transform
inject
block
```

Mental model:

```text
EventBus
= what happened?

HookPipeline
= may this happen / should it change?
```

This separation is one of the main architectural lessons of v0.5.

# 5. Extension module contract

Keep the educational API intentionally small.

Recommended shape:

```ts
export interface ExtensionDefinition {
  name: string;
  version?: string;
  setup(api: ExtensionAPI): void | Promise<void>;
}
```

An extension can be expressed as:

```ts
export default {
  name: "project-tools",

  setup(api) {
    api.registerTool(...);
    api.registerCommand(...);

    api.on("before_tool", async (event) => {
      // inspect or return a structured decision
    });
  }
} satisfies ExtensionDefinition;
```

The extension receives a narrow capability object rather than the concrete `Agent` instance.

Forbidden:

```ts
setup(agent: Agent) {
  agent.privateState.messages.push(...)
  agent.loopInternals = ...
}
```

Required:

```text
Extension
   ↓
ExtensionAPI
   ↓
stable runtime contracts
```

---

# 6. ExtensionAPI

Initial API:

```ts
export interface ExtensionAPI {
  registerTool(tool: Tool): void;
  registerCommand(command: CommandDefinition): void;

  on<K extends HookName>(
    hook: K,
    handler: HookHandler<K>
  ): Disposable;
}
```

Possible read-only helpers:

```ts
interface ExtensionAPI {
  readonly extensionName: string;

  getToolNames(): readonly string[];
  getCommandNames(): readonly string[];
}
```

Do not expose:

- direct mutable `AgentState`;
- raw private session internals;
- EventBus listener collection;
- scheduler implementation internals;
- provider transport internals.

The public API should expose capabilities, not object graphs.

---

# 7. ExtensionHost

Introduce one owner for loaded extensions:

```ts
export class ExtensionHost {
  load(extension: ExtensionDefinition): Promise<void>;
  unload(name: string): Promise<void>;

  list(): readonly LoadedExtension[];
}
```

Responsibilities:

- initialize extensions;
- create scoped `ExtensionAPI` instances;
- track registrations by extension;
- preserve deterministic load order;
- clean up registrations on unload;
- surface initialization failures clearly.

Non-responsibilities:

- running Agent turns;
- executing tools directly;
- constructing model context;
- rendering CLI/TUI.

---

# 8. Registration ownership

Every extension registration must record ownership.

Conceptually:

```ts
interface RegistrationOwner {
  extensionName: string;
}
```

Why?

Suppose extension `foo` registers:

```text
Tool: deploy
Command: /deploy
Hook: before_tool #17
```

If `foo` is unloaded, the runtime must be able to remove exactly those registrations.

Without ownership:

```text
load
load
reload
load
```

can accidentally produce duplicate handlers and stale tools.

Therefore registration is not just:

```text
registry.add(value)
```

It is conceptually:

```text
registry.add(owner, value)
```

This lays the groundwork for future reload/package support without implementing a full package manager in v0.5.

---

# 9. HookPipeline

Introduce:

```ts
export interface HookPipeline {
  run<K extends HookName>(
    hook: K,
    event: HookEventMap[K],
    context: HookContext
  ): Promise<HookResultMap[K]>;
}
```

The HookPipeline owns:

- handler ordering;
- sequential execution semantics;
- structured result combination;
- failure policy;
- cancellation propagation;
- tracing of hook execution.

The Agent Loop should not know which extensions are installed.

Correct:

```text
AgentLoop
   ↓
hooks.run("before_tool", ...)
   ↓
HookPipeline
   ↓
registered extension handlers
```

Incorrect:

```ts
if (hasExtension("permission-gate")) { ... }
if (hasExtension("project-policy")) { ... }
```

---

# 10. Deterministic hook ordering

v0.5 should prioritize understandability over sophisticated priority systems.

Recommended ordering rule:

```text
1. extensions execute in load order
2. handlers inside an extension execute in registration order
```

Example:

```text
load A
load B

A registers A1, A2
B registers B1

execution:
A1 → A2 → B1
```

Do not add numeric priorities in the first implementation unless a concrete invariant requires them.

Reason:

```text
priority=100
priority=50
priority=-1
```

quickly creates a hidden dependency graph that is harder to reason about than registration order.

If priorities become necessary later, they can be added as an explicit evolution of the hook contract.

---

# 11. Hook categories

Not every lifecycle point should have the same mutation power.

Use three conceptual categories.

## A. Observe

Handler sees data but returns no behavioral change.

Examples:

```text
after_model
after_turn
after_run
```

## B. Transform

Handler may return a structured replacement/addition.

Examples:

```text
before_model
before_tool
after_tool
```

## C. Gate

Handler may allow or block an operation.

Most important initial example:

```text
before_tool
```

This distinction prevents every hook from becoming an unrestricted mutation point.

---

# 12. Initial lifecycle hooks

Keep the first set compact.

Recommended:

```ts
type HookName =
  | "before_run"
  | "before_model"
  | "after_model"
  | "before_tool"
  | "after_tool"
  | "after_turn"
  | "after_run";
```

Do not mirror every internal function with a hook.

A hook is a public architectural commitment.

Before adding one, ask:

> Is this a stable lifecycle boundary that an extension legitimately needs?

---

# 13. `before_run`

Purpose:

- inspect a new user request;
- add run-scoped metadata;
- add context supplements;
- reject an invalid runtime configuration.

Example event:

```ts
interface BeforeRunEvent {
  input: string;
  runId: string;
}
```

Recommended result:

```ts
interface BeforeRunResult {
  supplements?: ContextSupplement[];
}
```

Do not allow arbitrary durable message mutation here.

---

# 14. `before_model`

Purpose:

- add or transform context supplements;
- adjust provider-neutral request options that the runtime explicitly exposes.

Conceptually:

```text
Session History
Skills
Extension supplements
      │
      ▼
before_model
      │
      ▼
ContextPlanner
      │
      ▼
LLMProvider
```

Or, depending on final v0.3 boundaries:

```text
ContextPlanner
      │
      ▼
PreparedContext
      │
      ▼
before_model transform
      │
      ▼
LLMProvider
```

The exact location must preserve one invariant:

> All extension-added model-visible content must still participate in context-budget accounting.

Extensions must not have a hidden path to append unlimited prompt text after budgeting.

---

# 15. `after_model`

Primarily observational in v0.5.

Possible uses:

- metrics;
- diagnostics;
- extracting extension-local metadata;
- trace annotations.

Do **not** initially allow arbitrary replacement of `AssistantMessage`.

Reason:

Changing assistant tool calls after model output can make tracing/session replay ambiguous.

If message replacement becomes necessary later, it should be introduced as an explicit, provenance-aware mechanism.

---

# 16. `before_tool` — most important hook

This is the strongest v0.5 interception point.

Input:

```ts
interface BeforeToolEvent {
  call: ToolCall;
  tool: Tool;
  runId: string;
  turn: number;
}
```

Return a structured decision:

```ts
type BeforeToolDecision =
  | { action: "continue" }
  | {
      action: "replace";
      arguments: Record<string, JsonValue>;
    }
  | {
      action: "block";
      reason: string;
    };
```

This allows extensions to implement behaviors such as:

```text
validate args
rewrite cwd-like parameters
apply project policy
block a call
```

without putting policy into each Tool implementation.

The scheduler receives the final approved call.

---

# 17. Hook composition for `before_tool`

Suppose three handlers run:

```text
A: continue
B: replace arguments
C: continue
```

The next handler should observe the transformed call produced by the previous handler.

Pipeline:

```text
original call
    ↓ A
call v1
    ↓ B
call v2
    ↓ C
call v2
    ↓
execute
```

If a handler returns:

```text
block
```

stop running later `before_tool` handlers for that call.

The blocked operation becomes an explicit runtime result rather than disappearing silently.

Recommended representation:

```text
ToolResultMessage
isError = true
content = "Tool call blocked by extension ..."
```

with trace provenance identifying the extension.

---

# 18. `after_tool`

Input:

```ts
interface AfterToolEvent {
  call: ToolCall;
  result: ToolResultMessage;
}
```

v0.5 may allow a constrained transform:

```ts
interface AfterToolResult {
  result?: ToolResultMessage;
}
```

Useful for:

- redaction;
- output normalization;
- adding structured metadata;
- truncation policy integration.

Important invariant:

> The original raw result should remain available to tracing/session policy when required; transformed model-visible output must have provenance.

Do not let `after_tool` mutate arbitrary earlier history.

---

# 19. `after_turn` and `after_run`

These should initially be observational/cleanup-oriented.

Examples:

```text
update extension-local metrics
flush extension state
release run-scoped resources
emit annotations
```

`after_run` should execute even when possible after controlled cancellation/error, with a status field:

```ts
type RunStatus =
  | "completed"
  | "cancelled"
  | "failed";
```

This makes cleanup deterministic.

---

# 20. Hook failures

Extension failures must not be ambiguous.

Define an explicit policy.

Recommended v0.5 default:

```text
intercepting hook failure
        ↓
fail the current operation/run visibly

observational cleanup hook failure
        ↓
record extension error
continue cleanup where safe
```

Do not silently swallow all extension exceptions.

Do not always crash the entire process either.

Introduce:

```ts
export class ExtensionHookError extends Error {
  extensionName: string;
  hook: HookName;
  cause: unknown;
}
```

Errors should identify:

- extension;
- hook;
- run/turn if applicable;
- original cause.

---

# 21. Cancellation

Every asynchronous hook should receive the run `AbortSignal`:

```ts
interface HookContext {
  signal: AbortSignal;
}
```

Architecture:

```text
Agent.abort()
    │
    ├── model stream
    ├── ToolScheduler
    ├── active Tool
    └── active Extension hook
```

Extensions must not create uncancellable hidden work inside the runtime path.

Background task management is out of scope for v0.5.

---

# 22. Custom tools

Extensions can register normal `Tool` objects:

```ts
api.registerTool({
  name: "project_status",
  description: "...",
  inputSchema: ...,
  execute: async (...) => ...
});
```

After registration, the tool goes through the exact same pipeline as built-ins:

```text
LLM ToolCall
    ↓
before_tool hooks
    ↓
ToolScheduler
    ↓
Tool.execute
    ↓
after_tool hooks
    ↓
ToolResult
```

No special extension execution path.

This is a critical invariant.

---

# 23. Tool name collisions

Define deterministic collision behavior.

Recommended v0.5 policy:

```text
duplicate tool name
        ↓
load error
```

Do not silently override a built-in or another extension tool.

Why?

Silent replacement makes the runtime behavior dependent on extension load order in a dangerous and opaque way.

A later version may add explicit override APIs if there is a justified use case.

---

# 24. Commands

Introduce a UI-neutral command abstraction:

```ts
export interface CommandDefinition {
  name: string;
  description: string;

  execute(
    args: string,
    context: CommandContext
  ): Promise<CommandResult>;
}
```

Commands are runtime/application actions initiated explicitly by the user.

Examples:

```text
/status
/tools
/skills
/project-check
```

A command is **not** an LLM Tool:

```text
Tool
model invokes it

Command
user/application invokes it
```

This difference should remain explicit.

---

# 25. CommandRegistry

Introduce:

```ts
export class CommandRegistry {
  register(owner, command): void;
  unregisterOwner(owner): void;
  get(name): CommandDefinition | undefined;
  list(): readonly CommandDefinition[];
}
```

The CLI can later route:

```text
input starts with "/"
      ↓
CommandRegistry
      ↓
execute command
```

The registry itself should not depend on terminal rendering.

This keeps v0.9 RPC/headless evolution possible.

---

# 26. Extension-local state

Extensions often need state.

Do not put arbitrary extension state into `AgentState`.

Recommended v0.5 model:

```text
LoadedExtension
    │
    └── extension-owned closure/object state
```

Example:

```ts
export default {
  name: "counter",

  setup(api) {
    let calls = 0;

    api.on("before_tool", () => {
      calls += 1;
      return { action: "continue" };
    });
  }
};
```

Persistent extension state is deliberately deferred.

Why?

Persistence introduces schema/version/lifecycle questions that deserve a separate design rather than silently stuffing extension data into session messages.

# 27. Discovery and loading

Keep initial discovery simple.

Recommended project location:

```text
.mini-pi/extensions/
├── project-policy.ts
└── project-tools/
    └── index.ts
```

Potential user location:

```text
~/.mini-pi/extensions/
```

However, v0.5 does not need to implement a package manager.

The first educational implementation can support:

```text
explicit extension paths
+
project-local discovery
```

The ExtensionHost should consume `ExtensionDefinition`; filesystem/module loading remains an adapter.

---

# 28. Trust boundary

Unlike Skills, Extensions execute code.

Therefore:

```text
Skill discovery
≈ read metadata/text

Extension loading
≈ execute trusted code
```

The runtime must treat them differently.

Rules:

1. never auto-execute arbitrary files merely because they resemble an extension;
2. only load configured/discovered extension roots with explicit policy;
3. surface which extensions were loaded;
4. make extension load failures visible;
5. never claim an Extension is sandboxed unless it actually is.

v0.8 will introduce the dedicated permission/sandbox model.

v0.5 should simply make the trust boundary explicit.

---

# 29. Extension lifecycle

Recommended lifecycle:

```text
discover module
      ↓
import module
      ↓
validate ExtensionDefinition
      ↓
ExtensionHost.load()
      ↓
create scoped ExtensionAPI
      ↓
setup(api)
      ↓
record registrations
      ↓
active
      ↓
unload
      ↓
dispose registrations/resources
```

Each registration returns/creates a cleanup handle internally.

Introduce a small primitive:

```ts
export interface Disposable {
  dispose(): void | Promise<void>;
}
```

This is enough to make unload deterministic.

---

# 30. Reload is not the first goal

A tempting feature is:

```text
edit extension.ts
      ↓
/reload
      ↓
hot swap everything
```

Do not make this the core of v0.5.

First prove:

```text
load
register
intercept
unload
cleanup
```

Only then is reload:

```text
unload + import fresh module + load
```

rather than a separate magic mechanism.

A basic reload example may be added after lifecycle invariants are proven, but production module-cache invalidation is a non-goal.

# 32. Integration with ToolScheduler

The scheduler remains responsible for execution coordination.

Target sequence:

```text
Assistant ToolCall[]
        ↓
for each call / scheduling unit
        ↓
before_tool HookPipeline
        ↓
approved/transformed call
        ↓
ToolScheduler
        ↓
Tool.execute
        ↓
after_tool HookPipeline
        ↓
ordered ToolResult[]
```

A hook must not bypass scheduling by calling the selected tool directly.

Otherwise timeout, cancellation, trace ordering and future permission policies are bypassed.

---

# 33. Integration with ContextPlanner

Extension-provided model context must use the same budgeted context path introduced in v0.3.

Preferred:

```ts
interface ExtensionContextSupplement {
  id: string;
  source: string;
  priority: number;
  content: string;
}
```

Then:

```text
Extension hook
      ↓
ContextSupplement
      ↓
ContextPlanner
      ↓
TokenEstimator / Budget
      ↓
PreparedContext
```

Forbidden:

```text
Extension
   ↓
raw string append after ContextPlanner
   ↓
Provider
```

because that defeats budget accounting.

---

# 34. Integration with Skills

Skills and Extensions should compose, not inherit from each other.

Example extension:

```text
company-workflows extension
      │
      ├── registers custom project tool
      └── contributes SkillSource
```

But a normal Skill should not require an Extension.

Conceptually:

```text
Skill
= knowledge package

Extension
= executable runtime plugin
```

Their installation/discovery mechanisms may converge later, but their trust and execution semantics must remain different.

---

# 35. Observability and provenance

Every runtime-changing hook should be traceable.

Recommended trace fields:

```ts
interface HookTraceRecord {
  hook: HookName;
  extensionName: string;
  startedAt: number;
  endedAt: number;
  outcome:
    | "continued"
    | "transformed"
    | "blocked"
    | "failed";
}
```

This allows a reader to answer:

```text
Why was this tool blocked?
Which extension changed these arguments?
Which hook added this context?
Which extension failed?
```

A customizable runtime without provenance becomes difficult to debug.

# 36. Tests required

## Extension loading

- valid extension loads;
- async setup is awaited;
- duplicate extension name fails;
- failed setup does not leave partial registrations;
- unload removes owned registrations.

## Hook ordering

- extension load order is preserved;
- handler registration order is preserved;
- transformed value is passed to next handler;
- block short-circuits later intercepting handlers.

## Error isolation

- hook error identifies extension/hook;
- initialization rollback removes partial registrations;
- cleanup continues where safe.

## Tool integration

- extension tool behaves like built-in Tool;
- before_tool can transform args;
- before_tool can block;
- after_tool can transform result;
- blocked calls produce explicit observations.

## Commands

- command registration/lookup;
- duplicate command collision;
- extension unload removes command.

## Cancellation

- aborted run aborts async hook;
- aborted hook does not execute tool afterward.

## Context integration

- extension supplements count toward context budget;
- extension cannot bypass planner through public API.

## Lifecycle

- setup → active → unload order;
- disposables run exactly once.

# 39. Explicit non-goals

v0.5 does **not** implement:

- npm/git extension package installation;
- remote extension marketplace;
- arbitrary code sandboxing;
- permission approval UI;
- persistent extension state schema;
- rich TUI widgets;
- keyboard shortcut framework;
- provider registration/replacement;
- sub-agent framework;
- numeric hook priorities;
- dependency graph between extensions;
- production hot-module reloading;
- MCP.

Those features either belong to later versions or should be justified by a concrete architectural need.

- [ ] scoped `ExtensionAPI` exists;
- [ ] `ExtensionHost` owns lifecycle;

- [ ] CommandRegistry exists;
- [ ] hook failure provenance is visible;

- [ ] no extension-specific branch exists in `runAgentLoop()`;

- [ ] at least one complete extension example works;
- [ ] docs explain Skill vs Extension vs Tool vs Command vs Event vs Hook;
- [ ] v0.4 behavior remains valid;

# 41. Learning goals

After v0.5, a reader should be able to explain:

1. Why an Extension is different from a Skill.
2. Why an Extension is trusted executable code.
3. Why Event and Hook should be different concepts.
4. Why a callback list alone is not enough to define a hook system.
5. Why hook ordering must be deterministic.
6. Why mutation must use structured return values rather than direct state access.
7. Why registration ownership is required for unload/reload.
8. Why tool interception belongs around ToolScheduler rather than inside every Tool.
9. Why extension-added prompt material must still obey context budgeting.
10. Why custom tools should use the same runtime path as built-in tools.
11. Why user Commands and model Tools are separate abstractions.
12. Why provenance is essential once plugins can change runtime behavior.

# 42. Next version dependency

v0.6 introduces MCP.

By the end of v0.5 the runtime will have a clean extension seam and stable Tool registration path:

```text
External MCP server
        ↓
MCP client adapter
        ↓
remote tool descriptors
        ↓
normal Tool objects
        ↓
ToolRegistry
        ↓
before_tool hooks
        ↓
ToolScheduler
        ↓
remote execution
```

This makes MCP a transport/tool-source problem rather than another special branch in the Agent Loop.

That is why Extensions should be understood before MCP.

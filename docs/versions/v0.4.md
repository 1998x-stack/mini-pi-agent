# mini-pi-agent v0.4 — Skills & Progressive Disclosure

Status: **implemented historical snapshot on branch `v0.4`**.

Package/runtime version: **`0.4.0`**.

Primary mental model:

> **A Skill is discoverable workflow knowledge, not an executor.**

Secondary mental model:

> **Available knowledge is not the same thing as model-visible context.**

---

# 1. Why Skills exist

The runtime already knew how to execute tools and how to derive a bounded model context from durable history.

What it did not have was a clean layer for repository- or task-specific workflow knowledge:

```text
code review
release preparation
incident diagnosis
migration planning
project conventions
```

Hard-coding that knowledge into `Agent` or `runAgentLoop()` would mix guidance with execution mechanics.

v0.4 adds a workflow-knowledge layer above the runtime.

---

# 2. Final architecture

```text
project SKILL.md packages
        ↓
ProjectSkillSource
        ↓
SkillDescriptor[]
        ↓
SkillRegistry
   ┌────┴───────────────┐
   │                    │
   ▼                    ▼
compact catalog    selected descriptor
   │                    │
   │                    ▼
   │             FilesystemSkillLoader
   │                    │
   │                    ▼
   │                LoadedSkill
   │                    │
   │                    ▼
   │          SkillActivationService
   │                    │
   │              ActiveSkillStore
   │                    │
   └────────────┬───────┘
                ▼
        ContextSupplement[]
                ↓
          ContextRuntime
                ↓
         PreparedContext
                ↓
           AgentLoop
```

The AgentLoop remains concrete-Skill-agnostic.

---

# 3. Skill / Tool / Extension boundary

```text
Skill
→ teaches workflow
→ model-facing knowledge
→ no hidden execution

Tool
→ executes environment capability
→ schema + executor

Extension (v0.5)
→ trusted executable runtime customization
→ lifecycle hooks / registrations
```

Strict rule:

```text
discover != load
load != activate
activate != execute
```

---

# 4. Progressive disclosure

```text
L0 descriptor
name + description

L1 active Skill
selected SKILL.md instructions

L2 references
ordinary explicit file-tool reads

L3 scripts/assets/templates
ordinary explicit tool paths
```

A catalog with many Skills therefore does not inject all full bodies into every request.

---

# 5. Package layout

Reference root:

```text
<cwd>/.mini-pi/skills/
```

Example:

```text
.mini-pi/skills/
└── code-review/
    ├── SKILL.md
    ├── references/
    │   └── security.md
    ├── scripts/
    │   └── changed-files.mjs
    └── assets/
        └── report-template.md
```

Only `SKILL.md` is required.

---

# 6. SKILL.md

```markdown
---
name: code-review
description: Review changes for bugs and regressions.
owner: project
---

# Code Review

1. Inspect changed files.
2. Identify behavioral changes.
3. Check tests.
```

v0.4 intentionally implements a deterministic scalar frontmatter subset.

Required:

```text
name
description
non-empty Markdown body
```

Unknown scalar metadata is preserved. Nested YAML, arrays, objects, block scalars, malformed lines, and duplicate keys are rejected explicitly.

---

# 7. Discovery and registry

`ProjectSkillSource` discovers:

```text
<cwd>/.mini-pi/skills/*/SKILL.md
```

and returns descriptor metadata only.

`SkillRegistry` uses:

```text
trim + lowercase
```

as normalized identity and rejects duplicate normalized names.

---

# 8. Safe loading

`FilesystemSkillLoader` loads one selected Skill only after:

```text
absolute-path validation
lexical root containment
exact root/SKILL.md identity
lstat real-directory/file checks
symlink rejection
realpath containment
manifest/descriptor identity validation
```

References, scripts, and assets remain unloaded.

---

# 9. Context supplements

v0.4 introduces generic model-only context material:

```ts
interface ContextSupplement {
  id: string;
  kind: "skill-catalog" | "active-skill";
  content: string;
  required: boolean;
}
```

Catalog supplements expose only `name + description`.

Active supplements expose full instructions for explicitly activated Skills.

Neither becomes a durable AgentMessage.

---

# 10. Budget accounting

Composition occurs before planning:

```text
base system
   ↓
summary checkpoint
   ↓
Skill supplements
   ↓
ContextPlanner
   ↓
PreparedContext
```

Skills are therefore only supported through `AgentOptions.context`; v0.4 does not bypass budgeting through the legacy ContextTransform path.

---

# 11. Activation

Shared service:

```text
SkillActivationService
        │
   ┌────┴─────┐
   ▼          ▼
load_skill   manual/API activation
   │          │
   └────┬─────┘
        ▼
ActiveSkillStore
```

Activation is normalized-name idempotent.

The store is run-scoped and clone-safe.

---

# 12. `load_skill`

The model activates a Skill through the existing ordinary Tool protocol:

```text
load_skill({ name: "code-review" })
```

ToolResult:

```text
Skill 'code-review' activated.
```

The full instructions are not returned as ToolResult content. They appear through an active Skill supplement on the next model turn.

---

# 13. Agent lifecycle

`Agent.create()`:

```text
discovers project Skills once
builds SkillRuntime
registers load_skill
```

Each `Agent.prompt()`:

```text
clear active store
      ↓
turn 1 sees catalog
      ↓
Skill may activate
      ↓
later turns see active body
      ↓
finally clear active store
```

This makes active Skills truly run-scoped.

---

# 14. Events

Skill lifecycle events:

```text
skill_activation_start
skill_activated
skill_activation_reused
skill_activation_failed
```

They contain metadata only.

When activation happens during an Agent run, `Agent` bridges these into the standard event stream with `runId` and `turn`.

---

# 15. References and scripts

There is no hidden Skill resource channel.

```text
references/*.md
→ ordinary file/read tool

scripts/*
→ ordinary explicit execution tool
```

This keeps future permissions/sandbox enforcement centralized in the normal execution path.

---

# 16. End-to-end proof

The v0.4 integration test and example establish:

```text
request 1
→ catalog only

load_skill("code-review")
→ compact durable acknowledgement

request 2
→ catalog + code-review body
→ unrelated Skill body absent

new Agent.prompt()
→ catalog only again
```

The selected Skill loader is invoked once; unselected full bodies remain unexposed.

---

# 17. Version result

v0.4 completes the Skills mental model:

```text
v0.3
History != Context

v0.4
Knowledge != Execution
Available Knowledge != Model-visible Context
```

The next snapshot, v0.5, moves from declarative workflow knowledge to trusted executable runtime customization through Extensions and lifecycle hooks.

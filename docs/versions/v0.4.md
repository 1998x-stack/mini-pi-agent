# mini-pi-agent v0.4 — Skills & Progressive Disclosure

Status: planned. Do not create the `v0.4` implementation branch until v0.3 is validated and integrated into `main`.

---

# 1. Version theme

v0.4 introduces the first **workflow knowledge layer** above the runtime:

> **A Skill is an on-demand package of instructions, references, scripts, and conventions. It changes what the agent knows how to do without changing how the Agent Runtime executes.**

The version exists to answer a practical question:

```text
The runtime already knows how to:
- call the model
- execute tools
- stream events
- schedule tool calls
- manage bounded context

How does the same runtime become good at:
- code review
- release preparation
- database migration
- PDF processing
- incident diagnosis
- repository-specific workflows

without hard-coding each workflow into Agent?
```

The answer is **Skills**.

---

# 2. Why v0.4 follows v0.3

The previous versions establish increasingly stable runtime mechanics:

```text
v0.1
model → tool → observation → model

v0.2
stream → assemble → schedule → ordered observations

v0.3
complete history → budgeted model context
```

Only after context preparation exists should the project add an on-demand knowledge layer.

Why?

Because Skills introduce a new context problem:

```text
10 skills × 4 KB each  = 40 KB
100 skills × 4 KB each = 400 KB
```

If every Skill is injected in full on every request, the architecture immediately fights the context-budget work from v0.3.

Therefore v0.4 must be built around **progressive disclosure**:

```text
startup / normal turn
        ↓
small Skill descriptors only
        ↓
model chooses a relevant Skill
        ↓
full Skill content is loaded on demand
        ↓
references/scripts/assets are loaded only when needed
```

This means v0.4 depends directly on the v0.3 distinction:

```text
available knowledge != model-visible context
```

---

# 3. Primary mental model

A Skill is not a Tool.

A Tool performs an environment action:

```text
Tool
=
schema
+
executor
```

A Skill provides operational knowledge:

```text
Skill
=
metadata
+
instructions
+
optional references
+
optional scripts/assets
```

The relationship is:

```text
                 ┌──────────────────────┐
                 │       Skill          │
                 │                      │
                 │ workflow knowledge   │
                 │ conventions          │
                 │ references           │
                 └──────────┬───────────┘
                            │ guides
                            ▼
User ─────► LLM ─────► Tool Calls ─────► Runtime
                            │
                            ▼
                       Environment
```

The Skill does **not** execute independently.

It changes the model's decision policy by adding relevant instructions and resources.

---

# 4. The most important architectural boundary

v0.4 must preserve:

```text
Runtime Mechanism
────────────────────────
Agent Loop
LLMProvider
ToolScheduler
ContextPlanner
SessionStore
Events


Workflow Knowledge
────────────────────────
SkillRegistry
SkillDiscovery
SkillLoader
SkillSelector
SkillActivation
```

Forbidden architecture:

```ts
if (skill.name === "code-review") {
  // special branch inside agent-loop.ts
}
```

Required architecture:

```text
Skill system
     │
     ▼
produces context/instructions/resources
     │
     ▼
ContextPlanner
     │
     ▼
normal Agent Loop
```

A new Skill must never require modifying `runAgentLoop()`.

# 5. Progressive disclosure

This is the central idea of v0.4.

Suppose the repository contains:

```text
skills/
├── code-review/
│   ├── SKILL.md
│   ├── references/
│   └── scripts/
├── release/
│   └── SKILL.md
├── database-migration/
│   └── SKILL.md
└── incident-debugging/
    └── SKILL.md
```

Do **not** construct the system prompt like this:

```text
FULL code-review SKILL.md
FULL release SKILL.md
FULL database-migration SKILL.md
FULL incident-debugging SKILL.md
...
```

Instead:

```text
Available Skills
────────────────────────────────────────
code-review
  Review code changes for correctness,
  regression risk, tests, and maintainability.

release
  Prepare and validate a software release.

database-migration
  Plan and verify schema migrations.
```

Then, if the user asks:

```text
Review this repository change.
```

The runtime/model activates:

```text
code-review
```

and only then loads:

```text
skills/code-review/SKILL.md
```

Potential reference files remain unloaded until requested.

Progressive levels:

```text
Level 0
Skill name + description

        ↓ selected

Level 1
SKILL.md full instructions

        ↓ needed

Level 2
references/*.md

        ↓ needed

Level 3
scripts / assets / templates
```

This gives Skills a natural relationship with context budgeting.

# 6. Skill package format

The educational package format should stay intentionally small.

Recommended structure:

```text
skills/
└── code-review/
    ├── SKILL.md
    ├── references/
    │   ├── checklist.md
    │   └── security.md
    ├── scripts/
    │   └── changed-files.mjs
    └── assets/
        └── report-template.md
```

Only `SKILL.md` is required.

Everything else is optional.

---

# 7. `SKILL.md` format

Recommended educational subset:

```markdown
---
name: code-review
description: Review code changes for bugs, regressions, missing tests, and maintainability issues.
---

# Code Review

## Workflow

1. Inspect repository status.
2. Read the changed files.
3. Identify behavioral changes.
4. Run relevant tests.
5. Report findings by severity.

## References

Read `references/checklist.md` when a deeper checklist is needed.
```

v0.4 should initially support only a small metadata set:

```ts
interface SkillManifest {
  name: string;
  description: string;
  metadata?: Record<string, string>;
}
```

Possible later fields should not be implemented merely because other harnesses support them.

Scope discipline matters more than format completeness.

# 8. Skill descriptor vs loaded Skill

Do not represent discovery and full loading as the same object.

Recommended types:

```ts
export interface SkillDescriptor {
  name: string;
  description: string;
  root: string;
  manifestPath: string;
}
```

This object is cheap and safe to keep in memory.

Full Skill:

```ts
export interface LoadedSkill {
  descriptor: SkillDescriptor;
  instructions: string;
}
```

The distinction matters:

```text
100 discovered skills
        │
        ├── 100 small descriptors
        │
        └── maybe 1-3 loaded Skill bodies
```

This is the data-model expression of progressive disclosure.

---

# 9. Skill discovery

Introduce:

```ts
export interface SkillSource {
  discover(context: SkillDiscoveryContext): Promise<SkillDescriptor[]>;
}
```

A source answers:

> Where can Skills be found?

Possible v0.4 sources:

```text
ExplicitSkillSource
ProjectSkillSource
UserSkillSource (optional)
```

Recommended first implementation:

```text
<cwd>/.mini-pi/skills/**/SKILL.md
```

Then optionally:

```text
~/.mini-pi/skills/**/SKILL.md
```

Dependency direction:

```text
filesystem
    ↓
SkillSource
    ↓
SkillRegistry
```

`Agent` must not scan directories itself.

---

# 10. SkillRegistry

The registry owns the discovered catalog.

```ts
export interface SkillRegistry {
  list(): readonly SkillDescriptor[];
  get(name: string): SkillDescriptor | undefined;
}
```

Responsibilities:

- store descriptors;
- enforce deterministic name collision policy;
- provide lookup;
- preserve discovery ordering rules.

Non-responsibilities:

- reading full instructions;
- selecting a Skill for a user request;
- executing scripts;
- modifying model context directly.

---

# 11. SkillLoader

Loading should be a separate concern:

```ts
export interface SkillLoader {
  load(
    descriptor: SkillDescriptor,
    signal: AbortSignal
  ): Promise<LoadedSkill>;
}
```

Why separate discovery and loading?

```text
Discovery
────────────────
cheap
metadata only
startup-friendly

Loading
────────────────
I/O
potentially larger
only when selected
```

This separation also enables future sources such as package registries or remote catalogs without changing the Skill consumer.

---

# 12. Skill selection

v0.4 should deliberately avoid a complicated embedding/RAG selector.

Start with the simplest useful architecture:

```text
Skill descriptors
      ↓
render into system/context section
      ↓
LLM sees names + descriptions
      ↓
LLM chooses when to activate
```

Possible explicit activation syntax for the educational CLI:

```text
/skill:code-review
```

This gives two paths:

```text
Automatic selection
user task
   ↓
model notices descriptor
   ↓
load Skill

Explicit selection
/skill:code-review
   ↓
load Skill directly
```

Do not add semantic search until the size of the catalog makes it necessary.

# 13. How does the model request a Skill?

There are two reasonable educational designs.

## Option A — Skill as a dedicated runtime action

Expose a tiny internal tool:

```text
load_skill(name)
```

The model sees descriptors and may call:

```json
{
  "name": "load_skill",
  "arguments": {
    "name": "code-review"
  }
}
```

The result returns the Skill instructions.

Advantages:

- reuses the existing ToolCall/ToolResult feedback loop;
- makes activation observable;
- requires little special model protocol;
- demonstrates that Skills can live above the runtime.

Potential drawback:

- a Skill is conceptually not an environment tool.

## Option B — dedicated Skill activation protocol

Add a separate runtime signal such as:

```ts
SkillActivationRequest
```

This is more semantically pure but introduces another model/runtime protocol.

### v0.4 recommendation

Use **Option A** initially:

```text
load_skill
```

but implement it through a Skill adapter layer so that the core Tool abstraction remains unchanged.

This is deliberately educational:

> Reuse the stable action/observation loop before inventing a second control protocol.

A later version can refine activation if evidence shows the abstraction is insufficient.

 ▼

 ▼

 ▼

 ▼

 ▼

# 15. Loaded Skill lifetime

A subtle design question:

```text
Once a Skill is loaded,
how long should it remain active?
```

Do not start with permanent global activation.

Recommended v0.4 policy:

```text
run-scoped activation
```

A run can track:

```ts
interface ActiveSkill {
  name: string;
  activatedAtTurn: number;
}
```

The Skill's full instructions may remain available for the current Agent run, subject to v0.3 context planning.

Future versions may introduce:

- session-persistent activation;
- project defaults;
- pin/unpin;
- activation priority.

Those are policy extensions, not v0.4 requirements.

# 16. Skill context integration

The Skill system should not concatenate strings directly into provider requests.

Preferred architecture:

```text
SkillRegistry
     │
     ├── descriptors
     │
ActiveSkills
     │
     └── loaded instructions
             │
             ▼
       ContextPlanner
             │
             ▼
      PreparedContext
             │
             ▼
        LLMProvider
```

This preserves the v0.3 rule:

```text
knowledge source != context construction
```

The ContextPlanner decides how descriptors and loaded Skill instructions fit into the token budget.

---

# 17. Context representation

Do not model all Skill text as ordinary user messages.

Introduce explicit context material, for example:

```ts
export type ContextItem =
  | MessageContextItem
  | SkillCatalogContextItem
  | ActiveSkillContextItem
  | SummaryContextItem;
```

Or keep the v0.3 planner API generic enough to accept context supplements:

```ts
interface ContextSupplement {
  id: string;
  kind: "skill-catalog" | "active-skill";
  priority: number;
  content: string;
}
```

The exact representation may depend on the final v0.3 implementation.

Important invariant:

> Skill knowledge must participate in the same context-budget accounting as all other model-visible material.

---

# 18. Skill catalog rendering

The descriptor catalog should be compact and deterministic.

Example:

```text
<available_skills>
  <skill name="code-review">
    Review code changes for correctness, regression risk and tests.
  </skill>
  <skill name="release">
    Prepare and validate a software release.
  </skill>
</available_skills>
```

The exact syntax is less important than these properties:

- small;
- deterministic;
- names unique;
- descriptions specific;
- easy for the model to map to `load_skill(name)`.

Do not include full instructions here.

---

# 19. References are also progressively loaded

Suppose:

```text
code-review/
├── SKILL.md
└── references/
    ├── frontend.md
    ├── backend.md
    ├── security.md
    └── testing.md
```

Loading `code-review` should not automatically load all references.

The Skill may say:

```text
For security-sensitive changes, read references/security.md.
```

The Agent can then use the existing `read` tool.

This is an important design simplification:

```text
SkillLoader loads SKILL.md

existing file tools load optional resources
```

No special `ReferenceLoader` is required in v0.4.

---

# 20. Scripts are not automatically trusted

A Skill package may contain helper scripts, but Skill discovery must not execute them.

Strict rule:

```text
discover != execute
load != execute
```

Execution occurs only through normal tools, such as the existing opt-in shell tool.

This preserves observability and later allows v0.8 permissions/sandbox policy to govern Skill-provided scripts naturally.

Architecture:

```text
Skill instructions
      ↓
model decides script is useful
      ↓
shell tool call
      ↓
normal ToolScheduler / permission path
```

Do not create a hidden Skill execution channel.

---

# 21. Path safety

A loaded Skill has a root directory.

Relative resources should resolve under that root.

```ts
interface LoadedSkill {
  descriptor: SkillDescriptor;
  instructions: string;
  root: string;
}
```

Skill-relative paths must not silently escape the Skill root when handled by Skill-specific helpers.

However, existing general filesystem tools continue to obey workspace-root rules.

These two roots should not be conflated.

---

# 22. Name collision policy

Discovery may find the same Skill name in multiple sources.

The policy must be deterministic.

Recommended v0.4 precedence:

```text
explicit source
    >
project source
    >
user source
```

Alternative policies are acceptable if documented, but "filesystem traversal happened to return this one first" is not acceptable.

The registry should emit a warning/event for collisions.

Possible event:

```ts
{
  type: "skill_collision",
  name,
  kept,
  ignored
}
```

---

# 23. Validation

A malformed Skill should fail clearly at discovery time when possible.

Validate at minimum:

- `SKILL.md` exists;
- frontmatter is parseable;
- `name` is non-empty;
- `description` is non-empty;
- name follows a simple safe pattern;
- duplicate names follow collision policy.

Recommended name rule:

```text
[a-z0-9]+(?:-[a-z0-9]+)*
```

Do not attempt a large specification implementation in v0.4.

---

# 24. Failure semantics

Different failures have different meanings.

## Discovery failure

Example:

```text
one malformed Skill among many
```

Recommended behavior:

```text
warning/event
+
skip malformed Skill
+
continue discovery
```

## Explicit Skill load failure

Example:

```text
/skill:missing-skill
```

Return a clear error.

## Model-requested load failure

The `load_skill` adapter should return a normal tool error observation when possible:

```text
ToolResultMessage(isError=true)
```

The Agent can then recover.

# 25. New event model

Add Skill lifecycle events without coupling UI to Skill internals.

Candidate events:

```text
skills_discovered
skill_collision
skill_load_start
skill_load_end
skill_load_error
skill_activated
```

Example trace:

```text
0ms   agent_start
2ms   skills_discovered(count=12)
5ms   turn_start
...
81ms  skill_load_start(code-review)
84ms  skill_load_end(code-review)
85ms  skill_activated(code-review)
...
```

This keeps Skill behavior inspectable.

# 29. Required tests

## A. Parser tests

- parses valid frontmatter;
- requires name;
- requires description;
- rejects invalid names;
- body is preserved as instructions.

## B. Discovery tests

- discovers nested `SKILL.md`;
- ignores unrelated files;
- deterministic ordering;
- malformed Skill does not destroy whole catalog.

## C. Collision tests

Given:

```text
user/code-review
project/code-review
```

project version wins according to policy.

## D. Progressive disclosure tests

Critical invariant:

```text
Skill catalog context
```

must contain descriptors but must **not** contain full Skill instructions before activation.

Then, after activation:

```text
active Skill instructions
```

must become available to ContextPlanner.

## E. Activation tests

- `load_skill(name)` loads known Skill;
- unknown Skill becomes recoverable tool error;
- loading same Skill repeatedly is idempotent or explicitly defined;
- abort propagates to loader.

## F. Context-budget tests

With many Skills:

- descriptor catalog is accounted for in budget;
- loaded Skill content is accounted for;
- history is not destructively changed.

## G. Security-boundary tests

- discovery never executes scripts;
- loading never executes scripts;
- Skill-relative helper paths cannot escape the Skill root.

# 31. Explicit non-goals

v0.4 does **not** implement:

- extension hooks;
- custom runtime plugin lifecycle;
- MCP transport;
- remote Skill marketplace;
- automatic Skill installation;
- cryptographic Skill signing;
- semantic/embedding Skill search;
- dependency resolution between Skills;
- Skill version solving;
- session branching;
- permission UI;
- process/container sandboxing;
- RPC protocol;
- multi-agent delegation.

Those belong to later architectural layers.

Recommended implementation order:

## v0.4.1 — Skill parser

Implement:

- frontmatter parser;
- metadata validation;
- `SkillDescriptor`;
- parser tests.

Learning target:

> A Skill is structured metadata + instructions, not arbitrary hidden prompt text.

## v0.4.2 — Discovery and Registry

Implement:

- `SkillSource`;
- project discovery;
- deterministic registry;
- collision policy.

Learning target:

> Discovery is resource indexing, not activation.

## v0.4.3 — Lazy SkillLoader

Implement:

- full `SKILL.md` loading;
- cache/idempotency policy;
- cancellation.

Learning target:

> Knowing that a capability exists is different from loading all of its knowledge.

## v0.4.4 — Catalog Context

Implement:

- compact descriptor rendering;
- ContextPlanner supplement integration;
- budget accounting.

Learning target:

> Context is a scarce runtime resource.

## v0.4.5 — Activation

Implement:

- `load_skill` adapter tool;
- ActiveSkill store;
- explicit CLI Skill activation.

Learning target:

> Workflow knowledge can be loaded through the existing Agent feedback loop.

## v0.4.6 — References and events

Implement:

- reference-path conventions;
- lifecycle events;
- collision/load diagnostics.

Learning target:

> Skills are observable packages, not invisible prompt mutation.

Implement:

- `code-review` Skill;

# 33. The conceptual progression so far

```text
v0.1 — Agent Loop
Question:
How does a model act on an environment?

        ↓

v0.2 — Streaming + Scheduler
Question:
How are model output and actions coordinated asynchronously?

        ↓

v0.3 — Context Budget + Compaction
Question:
How can the Agent keep running when history grows?

        ↓

v0.4 — Skills
Question:
How can the same runtime acquire specialized workflows on demand?
```

The progression is intentional:

```text
execution
   ↓
asynchrony
   ↓
long-running context
   ↓
on-demand capability knowledge
```

# 34. Why v0.5 comes next

Skills are mostly declarative:

```text
instructions
references
scripts/assets
```

They teach the model **how to work** while reusing existing runtime mechanisms.

The next architectural pressure appears when users need to modify the runtime itself:

```text
register a new tool
observe/intercept events
add commands
change lifecycle behavior
add UI integration
persist plugin state
```

That requires a different abstraction:

```text
Extension
```

Therefore the next version is:

```text
v0.5 — Extensions / Hooks
```

The distinction that must remain clear is:

```text
Skill
= workflow knowledge loaded by the agent

Extension
= executable code that extends the runtime
```

Keeping those concepts separate is the main architectural preparation v0.4 provides for v0.5.

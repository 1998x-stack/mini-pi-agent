# mini-pi-agent v0.4 — Skills & Progressive Disclosure

Status: **active design snapshot on branch `v0.4`**.

This version builds directly on the completed v0.3 context runtime.

Primary mental model:

> **A Skill is discoverable workflow knowledge, not an executor.**

Secondary mental model:

> **Available knowledge is not the same thing as model-visible context.**

---

# 1. Why Skills exist

The runtime already knows how to:

```text
model → tool intention → runtime execution → observation

and

complete history → budgeted PreparedContext → model
```

But those mechanisms do not teach the model repository- or task-specific workflows such as:

```text
code review
release preparation
incident diagnosis
migration planning
PDF processing
project-specific conventions
```

Hard-coding those workflows into `Agent` or `runAgentLoop()` would mix knowledge with execution mechanics.

v0.4 introduces a workflow-knowledge layer above the runtime.

---

# 2. Architecture

```text
filesystem Skill roots
        ↓
SkillSource
        ↓
SkillDescriptor[]
        ↓
SkillRegistry
   ┌────┴───────────────┐
   │                    │
   ▼                    ▼
compact catalog    selected descriptor
   │                    │
   │                    ▼
   │                SkillLoader
   │                    │
   │                    ▼
   │                LoadedSkill
   │                    │
   └────────────┬───────┘
                ▼
        Skill context material
                ↓
          ContextRuntime
                ↓
         PreparedContext
                ↓
           AgentLoop
```

The core AgentLoop must remain Skill-agnostic.

---

# 3. Skill / Tool / Extension boundary

```text
Skill
  teaches workflow
  model-facing knowledge
  no hidden execution

Tool
  executes an environment capability
  schema + executor

Extension (v0.5)
  trusted executable runtime customization
  registrations + lifecycle hooks
```

A Skill may contain scripts, but discovery/loading does not execute them.

```text
discover != execute
load != execute
```

If a Skill instructs the model to run a script, execution still travels through the ordinary shell/tool path and later permission policy.

---

# 4. Progressive disclosure

A catalog with 100 Skills must not inject 100 full documents into every request.

Disclosure levels:

```text
L0  descriptor
    name + description

L1  active Skill
    full SKILL.md instructions

L2  references
    read only when needed

L3  scripts/assets/templates
    inspect or execute only through normal tools
```

The default turn should pay primarily for L0 metadata and the small set of active L1 bodies.

---

# 5. Package layout

Reference root:

```text
<cwd>/.mini-pi/skills/
```

Example:

```text
.mini-pi/skills/
└── code-review/
    ├── SKILL.md
    ├── references/
    │   ├── checklist.md
    │   └── security.md
    ├── scripts/
    │   └── changed-files.mjs
    └── assets/
        └── report-template.md
```

Only `SKILL.md` is required.

# 6. SKILL.md format

Initial educational subset:

```markdown
---
name: code-review
description: Review changes for bugs, regressions, missing tests, and maintainability risks.
owner: project
---

# Code Review

## Workflow
1. Inspect changed files.
2. Identify behavioral changes.
3. Check tests.
4. Report findings by severity.
```

Supported metadata in v0.4:

```ts
interface SkillManifest {
  name: string;
  description: string;
  metadata?: Record<string, string>;
}
```

Parser rules:

- frontmatter is required;
- `name` and `description` are required non-empty strings;
- unknown scalar metadata may be preserved in `metadata`;
- nested YAML structures are intentionally out of scope for the first implementation;
- instructions are the body after frontmatter;
- discovery must not execute code.

---

# 7. Descriptor vs loaded body

Cheap descriptor:

```ts
interface SkillDescriptor {
  name: string;
  description: string;
  root: string;
  manifestPath: string;
  metadata?: Record<string, string>;
}
```

Loaded Skill:

```ts
interface LoadedSkill {
  descriptor: SkillDescriptor;
  instructions: string;
}
```

This distinction is the data-model form of progressive disclosure:

```text
100 descriptors in registry
≠
100 full Skill bodies in context
```

---

# 8. Discovery

```ts
interface SkillDiscoveryContext {
  cwd: string;
  signal: AbortSignal;
}

interface SkillSource {
  discover(context: SkillDiscoveryContext): Promise<SkillDescriptor[]>;
}
```

Initial source:

```text
ProjectSkillSource
→ <cwd>/.mini-pi/skills/*/SKILL.md
```

Discovery is deterministic:

```text
root order
then normalized Skill name order
```

Name collisions must fail explicitly rather than silently choose one descriptor.

Agent itself must not scan directories.

---

# 9. Registry

Reference contract:

```ts
interface SkillRegistry {
  list(): readonly SkillDescriptor[];
  get(name: string): SkillDescriptor | undefined;
}
```

Responsibilities:

- own descriptor catalog;
- deterministic ordering;
- normalized lookup;
- reject duplicate names;
- expose read-only copies/views.

Non-responsibilities:

- load full bodies;
- activate Skills;
- execute resources;
- mutate provider requests.

---

# 10. Loader

```ts
interface SkillLoader {
  load(
    descriptor: SkillDescriptor,
    signal: AbortSignal
  ): Promise<LoadedSkill>;
}
```

Reference loader re-reads/parses `SKILL.md` and verifies descriptor identity before returning instructions.

Important validation:

```text
manifestPath belongs to descriptor root
resolved path does not escape Skill root
parsed manifest name matches descriptor name
body is non-empty
abort propagates
```

Loading one Skill must not recursively load every reference/script asset.

---

# 11. Catalog rendering

Compact deterministic model-facing catalog:

```text
<available_skills>
<skill name="code-review">Review changes for bugs, regressions, missing tests and maintainability risks.</skill>
<skill name="release">Prepare and validate a software release.</skill>
</available_skills>
```

The renderer owns representation only. It does not select or activate Skills.

Requirements:

- stable ordering;
- XML-sensitive characters escaped or otherwise safely encoded;
- descriptors only;
- no full Skill instructions;
- small enough for context-budget accounting.

---

# 12. Context supplement seam

v0.3 currently prepares:

```text
base system prompt
+ optional summary checkpoint
+ recent AgentMessage[]
```

v0.4 must add Skill material without bypassing that budget path.

Reference design:

```ts
interface ContextSupplement {
  id: string;
  kind: "skill-catalog" | "active-skill";
  content: string;
  required: boolean;
}
```

The final implementation may refine fields, but supplements must be estimated and incorporated before the provider request is finalized.

Required ordering:

```text
base system instructions
summary checkpoint
Skill catalog
active Skill instructions
recent durable message tail
```

No post-planner raw append is allowed.

---

# 13. Activation

Recommended reference mechanism:

```text
LLM sees descriptor catalog
       ↓
ToolCall load_skill(name)
       ↓
SkillActivationTool
       ↓
Registry lookup
       ↓
SkillLoader.load()
       ↓
ActiveSkillStore.activate()
       ↓
ToolResult says Skill activated
       ↓
next model turn receives full active Skill instructions
```

This intentionally reuses the existing action/observation loop rather than introducing a second provider protocol.

`load_skill` does not return a giant hidden prompt outside the context system. It changes run-scoped activation state; the next context preparation exposes the loaded body as a budgeted supplement.

---

# 14. Run-scoped ActiveSkillStore

Reference shape:

```ts
interface ActiveSkill {
  skill: LoadedSkill;
  activatedAtTurn: number;
}

interface ActiveSkillStore {
  list(): readonly ActiveSkill[];
  get(name: string): ActiveSkill | undefined;
  activate(skill: LoadedSkill, turn: number): void;
  clear(): void;
}
```

Policy for v0.4:

```text
activation lifetime = one Agent.prompt() run
```

Starting a new run clears active Skill bodies while the catalog remains discoverable.

Repeated activation of the same Skill should be idempotent rather than duplicate full instructions in context.

---

# 15. References and resources

A Skill body may say:

```text
For security-sensitive changes, read references/security.md.
```

The model then uses the ordinary `read` tool.

The first version therefore does not need:

```text
ReferenceLoader
ReferenceRegistry
ReferenceExecutionProtocol
```

This is a deliberate simplification.

---

# 16. Path and trust boundaries

Two roots exist:

```text
workspace root
Skill package root
```

Skill-specific path helpers must never escape the Skill package root.

General file tools still obey the workspace root configured by Agent.

A Skill package is data/instructions at discovery/load time. Its scripts are not automatically trusted executable code. Hidden execution would violate the architecture and undermine later v0.8 permission policy.

# 17. Events

Recommended observational events:

```text
skill_discovery_start
skill_discovery_end
skill_activation_start
skill_activated
skill_activation_error
skill_context_prepared
```

Events may expose:

```text
runId
turn
skillName
descriptorCount
activeSkillCount
estimatedSkillTokens
```

Do not emit full Skill bodies by default.

# 20. Final acceptance invariants

A completed v0.4 must prove:

```text
1. discovering Skills does not execute package code
2. descriptors are cheaper than loaded bodies
3. duplicate Skill names fail deterministically
4. loading one Skill does not load all Skill resources
5. activation is run-scoped and idempotent
6. full Skill bodies enter model context only after activation
7. catalog and active bodies participate in context-budget accounting
8. Skill content never mutates durable conversation history
9. scripts execute only through ordinary tools
10. AgentLoop has no Skill-name-specific branches
11. deterministic tests need no live model
12. v0.3 context invariants remain intact
```

---

# 21. Non-goals

Not part of v0.4:

- Extension/hooks runtime;
- MCP;
- Skill marketplace/package install/update;
- remote catalogs;
- embeddings/RAG selector;
- dependency solving between Skills;
- permanent session/global activation;
- hidden script execution;
- permission/sandbox implementation;
- rich TUI;
- subagents;
- provider-specific Skill wire protocol.

---

# 22. Relationship to v0.5

v0.4 answers:

```text
How can the model learn an optional workflow?
```

v0.5 will answer a different question:

```text
How can trusted executable code intercept or extend runtime lifecycle behavior?
```

That separation is why Skill packages must stay declarative and non-executing in v0.4.
